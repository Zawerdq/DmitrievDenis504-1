## 1. Текущее состояние

### 1.1. Прошивка ESP32 — `src/web/DiffrentialControl_invert.ino`

Копия без изменений лежит в [firmware/upstream/](../firmware/upstream/DiffrentialControl_invert.ino).

| Что | Факт из исходника |
|---|---|
| Режим Wi-Fi | точка доступа: `WiFi.mode(WIFI_AP)`, `WiFi.softAP(ssid, password)` |
| SSID / пароль | в репозитории `bot1` / `12345678`; на роботе SSID `bot5` — значит, перед прошивкой строку меняли |
| IP-адрес | `softAPConfig` не вызывается → адрес по умолчанию **192.168.4.1** (совпадает с методичкой BOTS2026) |
| Протокол управления | **WebSocket**, `ws://192.168.4.1/ws`, порт 80, текстовые кадры с JSON |
| HTTP | `GET /` отдаёт страницу с джойстиком; других обработчиков нет |
| USB Serial | только отладочный вывод (115200 бод). **Команды по Serial не принимаются** |
| Данные от ESP32 к клиенту | нет (переменная `readings` не используется). Сервер отвечает только на WebSocket ping |
| Сборка | Arduino ESP32 core **2.0.15** (обязательно 2.x: используются `ledcSetup`/`ledcAttachPin`, удалённые в 3.x), Arduino_JSON 0.1.0, библиотеки из `libs/` |

Команды (каждая — отдельное JSON-сообщение):

| Сообщение | Действие |
|---|---|
| `{"x":X,"y":Y}`, X,Y ∈ −255…255 | джойстик: `left=(y+x)·invert1`, `right=(y−x)·invert2`, обрезка до ±255; оба нуля → `brake()` |
| `{"led":0\|1}` | светодиод GPIO2 |
| `{"fire":0\|1}` | силовой ключ (MOSFET) GPIO15, клеммник M3 |
| `{"invert1":0\|1}`, `{"invert2":0\|1}` | инверсия мотора; хранится в ОЗУ, сбрасывается при перезагрузке |

Защита в прошивке: если джойстик отклонён и сообщений нет **3000 мс** — моторы
останавливаются. При отключении клиента (`WS_EVT_DISCONNECT`) останов не выполняется —
только печать в Serial.

### 1.2. Драйвер TB6612FNG и распиновка

| Сигнал | GPIO ESP32 | Примечание |
|---|---|---|
| AIN1 / AIN2 | 13 / 14 | мотор 1 (канал A, клеммник M1) |
| BIN1 / BIN2 | 12 / 27 | мотор 2 (канал B, клеммник M2); GPIO12 — strapping-вывод |
| PWMA / PWMB | 26 / 25 | ШИМ 5 кГц, 8 бит, каналы LEDC 1 и 2 |
| STBY | 33 | до первой команды LOW (драйвер в standby), затем HIGH постоянно |
| MOSFET | 15 | strapping-вывод |
| LED | 2 | strapping-вывод, встроенный светодиод |

Библиотека `TB6612_ESP32` (из `libs/`): `drive(v)` — IN1/IN2 по знаку, ШИМ = |v|;
`brake()` — IN1=IN2=HIGH, ШИМ 0 (короткое замыкание обмоток, «short brake»).
Плавного разгона и ограничения тока в прошивке нет: реверс `+255 → −255` выполняется
мгновенно.

### 1.3. Схема платы BOTS PCB (rev 1.0, 2024-07-11)

Гнездо питания → выключатель → шина +12 В → VMOT драйвера, вход DC-DC, силовой ключ.
DC-DC +5 В → светодиод питания, ключ, через диод Шоттки 1N5822 → вывод 5V ESP32.

Наблюдения:

* Диод D1 стоит между шиной +5 В и выводом 5V ESP32 и не пускает ток от USB обратно
  в шину. По схеме это допускает подключение USB-кабеля к ESP32 при включённой батарее
  (на реальной плате не проверялось).
* На схеме **вывод VCC (питание логики) TB6612 никуда не подключён**. Если это так и на
  плате, логика драйвера питается «паразитно» через входы от GPIO — это возможная причина
  нестабильной работы и нагрева. Нужна проверка мультиметром (раздел 9.3).
* Предохранителя и электролитического конденсатора на шине моторов на схеме нет.
* В наборе BOTS стоит DC-DC «Amperka 5–12 В»; у вас указан DSN-MINI-360. Как именно он
  включён (вместо штатного или отдельно) — **не известно**.

### 1.4. Компьютер разработки (UltraMax)

Windows 11, Python 3.14, Git, Docker Desktop, WSL2 (Ubuntu 26.04, ROS 2 не установлен).
`arduino-cli` нет. `git clone` с github.com зависает (вероятно, ограничение сети),

## 3. Обнаруженные проблемы

### Прошивка

| № | Проблема | Важность |
|---|---|---|
| П1 | Таймаут потери связи 3 с: на полном ходу робот проедет заметное расстояние | высокая |
| П2 | При разрыве WebSocket моторы не останавливаются сразу (ждут те же 3 с) | высокая |
| П3 | Страница шлёт команды только при движении пальца: если держать джойстик неподвижно дольше 3 с, робот остановится сам | средняя |
| П4 | `JSON.parse((const char*)data)` — буфер не завершён нулём, возможен разбор мусора за концом кадра | средняя |
| П5 | Нет плавного разгона: мгновенный реверс даёт бросок тока до ~2× стопорного | высокая (нагрев TB6612) |
| П6 | Нет обратной связи: по сети нельзя узнать, что реально делает ESP32 | средняя |
| П7 | Несколько клиентов управляют одновременно, приоритета нет (телефон и мост будут мешать друг другу) | средняя |
| П8 | SSID в репозитории (`bot1`) не совпадает с роботом (`bot5`): точный прошитый исходник не сохранён | низкая |

### Электрика (по документам; измерений не было)

| № | Проблема | Что известно из документации |
|---|---|---|
| Э1 | Перегрев TB6612FNG | Допустимо 1.2 А в среднем на канал, 3.2 А в импульсе; VM до 13.5 В (предел 15 В). Стопорный ток ваших моторов **не известен**. У гусеничной платформы разворот на месте нагружает моторы почти до стопора |
| Э2 | Нагрев сразу при подаче питания | Без движения греться ничего не должно. Вероятные причины: не выставлено напряжение DSN-MINI-360 (он регулируемый), 12 В на выводе 5V/VIN ESP32, неподключённый VCC драйвера, переполюсовка, замыкание на выходах |
| Э3 | Питание Raspberry Pi 4 | Требуется 5.1 В, до 3 А. DSN-MINI-360 (MP2307) длительно держит ~1.8 А — для Pi 4 с USB-камерой и нагрузкой CV этого мало |
| Э4 | Батарея 3×18650 | 9.0–12.6 В. В простом держателе нет платы защиты: возможен переразряд и короткое замыкание без ограничения тока |
| Э5 | Помехи от моторов | Общая шина с ESP32 без конденсаторов → перезагрузки ESP32 при пуске моторов |

Программные меры, уже заложенные в узлы ROS 2: ограничение ШИМ (`max_duty: 0.6`),
плавный разгон и торможение через ноль при реверсе, запрет малых ШИМ, при которых мотор
стоит под током (`min_duty`). Они **снижают** нагрузку на драйвер, но не заменяют измерение
токов.

## 4. Связь Raspberry Pi ↔ ESP32: USB Serial или Wi-Fi

| Критерий | Wi-Fi (WebSocket) | USB Serial |
|---|---|---|
| Работает с текущей прошивкой | **да, без изменений** | нет — прошивка не читает Serial |
| Надёжность канала | зависит от радио; ESP32 рядом с Pi — обычно стабильно | выше: провод |
| Wi-Fi Raspberry Pi | занят сетью `bot5` (без интернета); для SSH нужен Ethernet или второй адаптер | свободен для SSH и видео |
| Веб-джойстик с телефона | сохраняется | сохраняется |
| Питание ESP32 | как сейчас | дополнительно от USB Pi (диод D1 это допускает) |
| Риски | обрыв радио, 4 клиента на точке доступа | при открытии порта ESP32 перезагружается (DTR/RTS) — решается программно |

**Решение.** Этап А (сейчас): Wi-Fi/WebSocket — единственный вариант, не требующий
перепрошивки рабочей ESP32, и его можно проверить немедленно. Этап Б (после вашего
подтверждения): добавить в прошивку приём тех же JSON-команд по Serial и перейти на
USB как основной канал; WebSocket остаётся для телефона. Мост уже построен так, что
транспорт — заменяемый модуль ([transport.py](../ros2_ws/src/susanin_esp32_bridge/susanin_esp32_bridge/transport.py)).

## 5. Доступность оборудования при аудите

* COM-портов нет → ESP32 по USB не подключена.
* Сеть `bot5` не видна, компьютер в домашней сети 192.168.3.0/24.
* В `known_hosts` есть `robot-pi.local` (к Pi уже подключались по SSH), но сейчас в сети
  нет ни одного устройства с MAC-адресом Raspberry Pi и открытым портом 22.
  (Имя `robot-pi.local` «резолвится» в 198.19.0.134 — это подставной адрес VPN-туннеля
  на компьютере, а не Pi.)

## 6. Архитектура ROS 2

```
  /cmd_vel (Twist)          susanin/track_cmd            WebSocket JSON
  телеоп / навигация / CV   [левая, правая] ∈ [-1,1]     {"x":..,"y":..} 20 Гц
        │                          │                            │
        ▼                          ▼                            ▼
  ┌──────────────┐          ┌───────────────────┐         ┌───────────┐      ┌─────────┐
  │susanin_control│────────▶│susanin_esp32_bridge│────────▶│  ESP32    │─────▶│ TB6612  │
  └──────────────┘          └───────────────────┘  Wi-Fi  └───────────┘      └─────────┘
        ▲      ▲                   │      ▲          bot5
        │      └───────────────────┘      │
  susanin/e_stop      susanin/esp32/connected, /diagnostics
```

| Пакет | Назначение |
|---|---|
| `susanin_control` | `/cmd_vel` → ограничение скоростей → кинематика гусениц → рампа → запрет «мёртвых» ШИМ; таймаут команд; аварийный останов; обнуление при потере связи |
| `susanin_esp32_bridge` | перевод команд гусениц в протокол прошивки; отправка 20 Гц; свой сторожевой таймер; ping/pong; переподключение; диагностика; эмулятор прошивки |
| `susanin_bringup` | launch-файл и единственный YAML с параметрами |

`susanin_interfaces` не создавался: хватает стандартных сообщений.
Отдельного «bringup-узла» нет: запуск и перезапуск упавших узлов делает launch
(`respawn`), состояние связи публикует мост — лишний узел ничего бы не добавил.

Подробности интерфейсов: [INTERFACES.md](INTERFACES.md).

### Цепочка остановов (от быстрого к медленному)

| Событие | Кто останавливает | Время |
|---|---|---|
| `susanin/e_stop = true` | узел управления и мост, независимо | ≤ 0.1 с |
| нет `/cmd_vel` | узел управления (плавно) | 0.5 с + торможение |
| узел управления завис/упал | мост: команда устарела → ноль | 0.5 с |
| ESP32 не отвечает на ping | мост: разрыв, переподключение; узел управления обнуляет рампу | 1.5 с |
| мост завершён штатно | последним сообщением уходит `{"x":0,"y":0}` | сразу |
| мост упал / пропал Wi-Fi | **только прошивка** | **3 с** (П1, П2) |

Последняя строка — причина, по которой правки прошивки Ф1–Ф2 (раздел 8) важны.

## 8. Необходимые изменения существующего кода (НЕ внесены, требуют согласования)

Для первого запуска через ROS 2 менять прошивку **не нужно**. Изменения ниже повышают
безопасность; каждое — небольшое дополнение, распиновка, ШИМ и микшер не затрагиваются.

| № | Изменение | Зачем |
|---|---|---|
| Ф1 | `COMMAND_TIMEOUT` 3000 → 500 мс **и** в странице повторять последнюю команду каждые 100 мс, пока палец на джойстике | П1, П3; без второй части веб-джойстик перестанет работать при удержании |
| Ф2 | В `WS_EVT_DISCONNECT`: если клиентов не осталось — `brake()` | П2 |
| Ф3 | Копировать кадр в буфер с завершающим нулём перед `JSON.parse` | П4 |
| Ф4 | Сохранить в нашем репозитории исходник ровно в том виде, в каком он прошит (SSID `bot5`) | П8, воспроизводимость |
| Ф5 | (этап Б) приём тех же JSON-строк из Serial; периодическое сообщение о состоянии | USB-канал, П6 |

Перепрошивка — только с вашего подтверждения и только при вывешенных гусеницах.

## 9. Команды диагностики

### 9.1. Raspberry Pi (нужен результат, чтобы выбрать версию ROS 2)

```bash
bash scripts/pi_diagnostics.sh | tee pi_report.txt
```

Скрипт ничего не меняет. Если репозитория на Pi ещё нет — скопируйте один файл
[scripts/pi_diagnostics.sh](../scripts/pi_diagnostics.sh).

Правило выбора: Ubuntu 24.04 arm64 → ROS 2 Jazzy; Ubuntu 22.04 arm64 → Humble;
Raspberry Pi OS 64-бит → ROS 2 в Docker или переустановка Ubuntu Server 24.04;
32-битная ОС → переустановка обязательна. Подробнее: [SETUP.md](SETUP.md).

### 9.2. ESP32 (с ноутбука, подключённого к Wi-Fi `bot5`; моторы не включаются)

```bash
python scripts/esp32_probe.py --led-blink --seconds 10
```

Ожидается: связь установлена, задержка ping/pong в десятки миллисекунд, светодиод на ESP32
мигает, переподключений 0.

### 9.3. Измерения мультиметром (питание выключено, если не сказано иное)

1. Сопротивление обмотки каждого мотора (моторы отключены от платы), Ом.
   Стопорный ток ≈ 12 В / R. Если он больше 1.2 А — `max_duty` в YAML должен быть
   не выше `1.2 / I_стоп`.
2. Напряжение на выходе DSN-MINI-360 **без нагрузки**: должно быть 5.0–5.2 В.
   Если больше — не подключать ни ESP32, ни Pi, пока не отрегулировано.
3. При включённом питании, моторы отключены: напряжение на выводах TB6612
   VM (ожидается 9–12.6 В), VCC (ожидается 3.3–5 В), на выводе 5V ESP32 (≈4.7–5 В).
4. Напряжение каждого аккумулятора по отдельности.
5. Что греется при подаче питания без команд (осторожно, пальцем не более секунды).
